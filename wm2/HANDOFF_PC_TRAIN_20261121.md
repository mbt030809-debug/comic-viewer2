# 핸드오프: wm2 워터마크 인식 — PC/GPU 학습 세션용 (2026-11-21)

이 문서만 읽고 이어서 작업할 수 있게 쓴 것이다. 작업 폰(Termux, CPU만)에서 한 실험 결과와, PC에서 해 볼 실험을 적었다.

**이 PC 세션의 전제**: GPU가 있고 **작업량이 많아도 된다**(사용자 허락). 폰에서는 CPU 시간 때문에 못 한 큰 실험을 한다. **결과는 사용자를 거치지 않고 GitHub에 직접 올리고(§7), 이 폰 세션이 이어받을 귀환 핸드오프 문서를 직접 쓴다(§7-2).**

## 0. 지켜야 할 규칙 (사용자 지시)
- **코드 변경은 브랜치 `wm2-recognition`, 결과물 업로드는 브랜치 `wm2-pc-results`(새로 만들어 사용)에만 푸시한다(사용자가 이 두 브랜치 푸시를 허락함).** `main` 푸시 금지: main 푸시 시 CI가 `latest` 릴리스를 만들고 사용자 폰 앱이 자동 업데이트 알림을 받는다. `main`이나 다른 브랜치로 푸시할 일이 생기면 먼저 사용자에게 묻는다. **GitHub Release를 만들지 않는다**(만들면 앱 자동 업데이트가 쓰는 `latest`가 바뀔 수 있다). 원본 `comic-viewer` 저장소에는 푸시·PR 금지.
- 답변은 한국어, 짧게, 개조식. **정직하게**: 합성 시험 결과와 실기기 결과를 구분하고, 확인 못 한 것은 못 했다고 쓴다.
- 결과 파일 이름 끝에 날짜(_YYYYMMDD). 저작권 있는 웹툰 이미지는 저장소에 올리지 않는다(이 저장소의 시험 자료는 전부 합성이다).
- 커밋 꼬리말: `Co-Authored-By: ...` 와 `Claude-Session: ...` (현재 세션 정보).

## 1. 목표
웹툰 사이트가 이미지에 구운 **반투명 워터마크**(로고·글자·원형 도장·전면 반복 무늬 등)를, 같은 사이트의 이미지 여러 장(3~8장)에서 **자동으로 인식**해 상자로 돌려주는 것. 제거는 범위 밖(인식이 먼저). 최종 목표는 안드로이드 앱 안에서 도는 것(ONNX Runtime 사용 중).
- 워터마크의 모양·색·위치는 사이트마다 다르고 자주 바뀐다. **"반복해서 나온다"가 특징**이지만, 위치·크기가 장마다 달라지는 사이트도 있다.
- 사용자 원칙: 단순한 선은 워터마크가 아니다(컷 테두리·구분선). 인식 못 하면 의미 없고, **멀쩡한 이미지를 지우는 오인식은 더 나쁘다**.

## 2. 지금까지 결과 (폰 CPU, 합성 벤치 core 128개 사이트·756장, IoU≥0.5가 맞음)
| 방식 | 인식률 | 워터마크 없는 이미지 오인식 |
|---|---|---|
| 정렬 합의(여러 장을 같은 위치로 겹쳐 방향 일치도 측정, `Wm2.kt`) | 30~34% | 23~77% |
| 쌍 변위(FFT 상관, `Wm2Pair.kt`) | ~0% | 매우 많음(합성 만화의 반복 구조에 우연 일치) |
| 학습형 U-Net 단독(0.2M, 3만 샘플, 폰 CPU 2,500스텝) | **51.5%** | **99%** (정밀도 4.4%) |
| 학습형 + 확률 지도 NCC 반복 확인(`hybrid.py`) | 46.7% | 100%, 상자 3.9만 건, 58분(실패) |
| 공개 SLBR(21M, 16장 시험) | 양성 13장 중 6장 | 있음, 이미지당 60~150초(앱 불가, 라이선스 미명시) |

해석:
- 학습형은 위치가 제각각인 종류에 강하다(free_y 67%, random 61%, scaled 69%). 그러나 **한 장만 보면 말풍선·글자와 도장을 못 가린다**(같은 글꼴이면 원리상 어렵다).
- 학습은 손실이 ~1.0에서 느리게 내려가는 중이었다 → **학습량·용량 부족이 확실히 있다**. 단, 학습량/용량만으로 오인식이 사라지는지는 **검증하지 못했다**(공개 SLBR도 음성 이미지에서 오인식).
- 그래서 단독 학습형은 **"후보 제안"**으로 쓰고, 오인식은 다른 근거(반복·사용자 확인)로 막는 구조를 가정하고 있다. 아래 §5 실험이 이 가정을 검증한다.

## 3. 저장소 구조 (`wm2-recognition` 브랜치)
- `wm2/tools/gen_bench.py` — 벤치마크 생성기(만화 + 워터마크 종류·위치·투명도 조합, 정답 `truth.json`, 정답지 `answer.html`). 같은 seed면 같은 결과. 티어 `core`(체계적 128개)·`wild`(무작위 120개)·`val`(다른 seed·따로 둔 글꼴 60개).
- `wm2/tools/eval_bench.py` — 평가(IoU≥0.5, 카테고리별 인식률·엉뚱한 상자·음성 이미지 오인식률).
- `wm2/train/` — `model.py`(U-Net), `synth.py`(학습 데이터 즉석 합성), `build_pool.py`(배경·스프라이트 풀), `train.py`, `infer_eval.py`(벤치 추론→예측 tsv), `infer_maps.py`, `hybrid.py`(실패, 참고용).
- `app/src/main/java/com/example/comicviewer/wm2/` — 순수 Kotlin 엔진(정렬 합의, FFT 쌍). `wm2/test/Wm2Bench.kt` JVM 하니스, `wm2/tools/build.sh`(폰용 경로 가정, PC에서는 경로 수정).
- `handoff/PLAN_wm2_recognition_20261121.md` — 초기 플랜(방법론 일부는 위 결과로 폐기됨).

## 4. PC 환경 준비
```
git clone <저장소> && cd <저장소> && git checkout wm2-recognition
pip install torch pillow numpy scipy          # GPU 버전 torch 권장
export WM2_FONT_DIR=/경로/글꼴폴더/             # 선택. 없으면 대체 글꼴(DejaVu 등) 자동 사용
export WM2_FALLBACK_FONT=/경로/한글글꼴.ttf     # 한글이 나오는 글꼴 하나(예: NotoSansCJK)
python3 wm2/tools/gen_bench.py --tier core --out ~/wm2-bench --jobs 4     # 평가용
python3 wm2/tools/gen_bench.py --tier val  --out ~/wm2-bench --jobs 4
python3 wm2/tools/gen_bench.py --tier wild --out ~/wm2-bench --jobs 4
python3 wm2/train/build_pool.py --out ~/wm2-train --nbg 12000 --nspr 20000 --jobs 8   # 풀을 폰보다 10배로
```
- **주의: 글꼴이 폰과 달라 PC 벤치는 폰 벤치와 이미지가 다르다.** 숫자를 폰 결과와 직접 비교하지 말고, 같은 PC 벤치에서 기준선(아래 §5-0)을 다시 잰다. 폰과 똑같은 벤치가 필요하면 사용자에게 `~/wm2-bench/core`를 받는다(약 500MB).
- 학습 합성기는 `synth.py`가 `bgs.npy`(mmap)와 `sprites.pkl`을 읽는다. 풀을 키우면 메모리 확인.

## 5. 해 볼 실험 (우선순위)
0. **기준선**: PC 벤치에서 폰의 U-Net(`train.py` 기본 설정, 2,500스텝)을 다시 학습·평가해 폰 수치(인식 51.5%/음성 오인식 99%)가 재현되는지 본다. 평가: `python3 wm2/train/infer_eval.py <ckpt> ~/wm2-bench/core <out.tsv>` → `python3 wm2/tools/eval_bench.py ~/wm2-bench/core/truth.json <out.tsv> --fail fail.txt`.
1. **진단(병목 가르기)**: ① 샘플 200개만 반복 학습해 손실이 0 근처로 가는지(용량 충분 여부) ② 학습량 3천/3만/10만 스텝에서 검증 곡선 ③ 채널 2배·4배(`--ch 16,32,64,96,128` 등). **체크포인트 선택은 "음성 이미지 오인식률"과 "인식률"을 같이 본다**(픽셀 IoU만 보지 않는다 — 폰에서 픽셀 IoU는 좋아 보여도 오인식이 심했다).
2. **하드 네거티브**: 합성기에서 빈 조각 비율을 올리고(현재 약 20%), 말풍선·본문 글자·인물·직선·같은 글꼴의 비워터마크 글자를 일부러 많이 넣는다. 정답 마스크에는 "눈에 보이는 도장만"(합성 전후 변화량 95백분위≥5)을 쓴다(`synth.py` 반영됨).
3. **반복 정보를 모델 안으로**: 같은 사이트 2~3장을 함께 입력(채널 연결 또는 후보 크롭 쌍 판별기). 한 장 단독의 구조적 한계(§2)를 넘으려는 시도.
4. **앱 배포 제약**: ONNX opset 17로 내보내져야 한다(사용자 정의 연산 금지: SLBR은 변환 실패). 목표 ≤ 2~4M 파라미터, 폰 CPU에서 이미지 한 장(0.5배 축소 360×~950) 몇 초 이내. 큰 모델로 학습 후 증류·int8 양자화도 후보.
5. 가능하면 **사이트당 한 번**(3~8장만 큰 모델로) 인식하고 나머지 장은 가벼운 템플릿 매칭으로 찾는 구조를 가정해도 된다.

## 5-2. GPU가 있으니 추가로 해 볼 큰 실험
- **큰 선생 모델로 상한 확인**: U-Net 채널 4~8배 또는 SegFormer/Swin-U 계열(20~40M)로 수십만~수백만 샘플 학습. "모델·학습량을 최대로 키우면 오인식이 얼마나 내려가나"가 핵심 질문이다. 이 상한이 낮으면(음성 오인식이 높게 남으면) 단독 학습형은 접고 §5-3·반자동 방향을 제안한다.
- **데이터 다양화**: 합성기의 워터마크 종류·글꼴·색·투명도·위치 분포를 넓히고, 배경 풀을 크게(수만 장). 가능하면 사용자에게 실제 웹툰 배경(워터마크 없는 것)을 받아 섞는다(저장소에는 올리지 않는다).
- **증류·양자화**: 선생 → ≤2~4M 학생(ONNX opset 17, int8 시험). 학생의 ONNX 모델을 폰 CPU에서 몇 초에 도는지는 이 폰 세션이 잰다(PC에서는 입력 크기·연산 수만 보고한다).
- **공개 모델은 연구 비교용으로만**: SLBR·WMFormer++ 등은 라이선스가 명시돼 있지 않다. 상한 비교에만 쓰고, 앱 배포 모델에는 쓰지 않는다.
- **독립 검증**: val 티어(다른 seed·따로 둔 글꼴)는 끝에서만 본다. 학습 때 쓰지 않은 합성 분포(새 글꼴·새 종류)로 일반화도 잰다.

## 6. 목표치 (합의 필요 시 사용자에게 확인)
core 인식률 ≥ 80%, **음성 이미지 오인식 ≤ 5%**, wild·val에서 비슷하게 유지(수정 중에는 val을 보지 않고 끝에서만 확인). "애매함"(`decoy_footer`, 글자가 든 고정 띠)은 오인식으로 세지 않고 따로 집계한다.

## 7. 돌려줄 것 — GitHub에 직접 올린다
**7-1. 결과물 업로드** (브랜치 `wm2-pc-results`, `wm2-recognition`에서 갈라져 나온다):
```
git checkout -b wm2-pc-results wm2-recognition
mkdir -p wm2/results/YYYYMMDD
# 넣을 것: 평가 tsv·fail 목록, 학습 로그(요약), 실험 표(마크다운), 체크포인트(.pt = state_dict+ch만)·ONNX(.onnx) — 각 파일 50MB 이하
git add wm2/results/YYYYMMDD && git commit && git push origin wm2-pc-results
```
- 파일이 50MB를 넘으면 올리지 말고 크기·해시·재현 명령만 기록한다(LFS·Release 사용 금지).
- 코드 변경(합성기·학습·평가 개선)은 `wm2-recognition`에 푸시해도 된다.
- 실험 표에는 **실험마다** 설정(모델 크기·샘플 수·스텝), core/wild/val 인식률, **음성 이미지 오인식률**, 추론 시간(PC), 모델 파라미터 수를 적는다.

**7-2. 귀환 핸드오프 문서 `wm2/RETURN_HANDOFF_YYYYMMDD.md`** (이 폰 세션이 이어받을 문서; `wm2-pc-results`에 함께 푸시). 반드시 포함:
1. 한 줄 결론: 목표치(§6)를 달성했나, 어디까지 갔나.
2. 가정 검증 결과: 병목이 모델 크기/학습량/문제 설정(한 장 구분 한계) 중 무엇이었나. 근거 수치.
3. **추천 모델 하나**와 사용법: 파일 경로, 입력 정규화(예: RGB 0~1)·입력 크기(0.5배 축소 등)·출력 의미·권장 임계값·후처리(덩어리 → 상자 변환, 전면 무늬 판정)·ONNX 입출력 이름과 형상.
4. 앱 연결 계획 초안: 사이트당 몇 장을 모델에 넣고 나머지는 템플릿 매칭으로 찾을지, 오인식 방어(여러 장 확인·사용자 확인) 방식.
5. 한계·모르는 것(실기기 미검증, 합성 분포 밖 성능 등)을 솔직하게. 합성 결과와 실제 웹툰 결과를 구분해 적는다.
6. 폰 세션이 할 일 목록(ONNX를 앱에 넣고 폰 CPU 시간 측정, 독립 36장·실제 이미지 시험, 앱 연결 순서).
7. 재현 명령(데이터 생성 seed·학습 명령·평가 명령).

## 8. 알아 둘 함정
- `truth.json`의 `visible=false`(대비<3) 워터마크는 인식률 계산에서 빠진다. `expected`는 `mark`/`none`/`ambiguous`.
- `tiled`(전면 반복)는 정답 상자가 이미지 전체, `band`는 가로 전체 폭이다.
- 폰 쪽 기존 앱 코드(`WmCore.kt`, `WmEngine.kt`, 지우기 포함)는 건드리지 않았고, wm2는 별도 패키지다. 앱 연결(ONNX 추론 + 사이트당 확인)은 인식이 목표치를 넘은 뒤에 폰 세션에서 한다.
